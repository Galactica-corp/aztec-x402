# Защита от повторного использования платежа (anti-replay)

## Что было

Раньше сервер проверял оплату так: "баланс >= нужная сумма". Проблема — один и тот же платёж можно предъявить повторно. Клиент заплатил один раз, но может отправить тот же заголовок `PAYMENT-SIGNATURE` много раз и получать данные бесплатно.

Это называется **replay-атака** — повторное воспроизведение перехваченного запроса.

## Что сделали

Добавили in-memory Set хешей использованных транзакций в фасилитатор. Три изменения в одном файле (`packages/mechanism/src/exact/facilitator/scheme.ts`):

1. **Хранилище**: `private consumedTxHashes = new Set<string>()` — запоминает все использованные txHash
2. **Проверка при верификации**: если txHash уже в Set → отклоняем с ошибкой "payment already used"
3. **Запись при подтверждении**: после успешного settle добавляем txHash в Set

## Как это работает

```
Клиент платит (txHash: abc123) → verify() проверяет: abc123 в Set? Нет → OK
                                  settle() записывает abc123 в Set

Клиент повторяет тот же платёж → verify() проверяет: abc123 в Set? Да → 402 "payment already used"

Клиент платит снова (txHash: def456) → verify(): def456 в Set? Нет → OK
```

## Проверка

Написали тест `replay-test.ts` который:
1. Получает 402 от сервера (нужно заплатить)
2. Создаёт реальный платёж, отправляет → 200 (успех)
3. Отправляет тот же самый заголовок ещё раз → 402 "This payment has already been consumed."

Результат: защита работает.

## Ограничения

- **In-memory** — при перезапуске сервера Set очищается. Для продакшена нужна персистентная база (Redis, БД).
- **Не защищает от других серверов** — если тот же платёж отправить другому серверу, он его примет. Полная защита требует проверки nonce заметок на уровне PXE.

Это первый шаг. Полная защита через nonce — отдельная задача.
